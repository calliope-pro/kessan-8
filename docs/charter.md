# プロジェクト方針 (charter)

状態: 技術責任者が決めた (2026-11-04)。人間の承認は non-blocking (人間の指示「朝には完成しておいて」により、承認を待たずにこの方針で進め、朝に理解の表で確かめる)。

## 高くつく失敗

1. 異変の無いはずの資料が会計の整合を破っていて、正しく答えた遊び手が不正解になる (ゲームが成り立たない)
2. 異変の判定や答え合わせの表示が、問題のデータと食い違う
3. 実在の企業名・秘密が公開リポジトリと公開サイトに入る
4. 朝までに遊べる版が無い (期限)

## 原則

| 原則 | 選んだ理由 (効く失敗) | 選ばなかったら |
| --- | --- | --- |
| single source of truth | 問題の数字・異変の定義・答え合わせの文言を、問題のデータ 1 か所から作る (失敗 1・2) | 画面と答え合わせで数字がずれる |
| テスト容易性 | 会計の整合を検証器で全問に機械的に当てる。異変の問題は「指定した規則だけが破れている」ことを確かめる (失敗 1) | 正常な問題に紛れた不整合を人の目で探すことになる |
| セキュリティ | 公開リポジトリ・公開サイト。秘密を置かない。外部への通信をしない静的サイト (失敗 3) | 秘密や実名が公開される |
| AI エージェントとの親和性 | 作るのも直すのも AI。ファイルを小さく、型で境界を示す | 文脈に入り切らず、手戻りが増える |
| 保守性 (控えめ) | 公開後は誤りの訂正だけ (要件)。問題の追加はデータを足すだけで済む形にする | 訂正のたびに画面のコードを触る |

順位は付けない。ぶつかったら技術責任者が決め、チケットに記録する。DRY・SOLID は、上の原則に反しない範囲の既定の作法として扱い、それ自体を理由に指摘しない (期限があるため)。

## 実践 (既定から変えるもの)

- テスト: orchestrating-develop の testing の既定どおり (ケース表 → レッド → グリーン)。ただし問題データ (JSON) の中身は、ケース表ではなく検証器 (全問に当てる) で確かめる
- E2E: Playwright で受け入れ条件 1〜4・9 を 1 本ずつ。スマホの幅は 375 px で 1 本
- レビュー: Sub-task ごとの監視役のレビュー、Task・Story の包括レビューは既定どおり
- 期限のため、Task の包括レビューで「不可」が出ても、指摘が blocking でなければ、同じ組が直して組の監視役が確かめれば完了にしてよい (blocking の指摘があれば、関わっていない監視役がもう一度見る)

## 品質の水準

- 静的サイト・利用者は少数・費用 0 円。可用性の約束は無い
- 対応ブラウザ: 最新の Chrome・Safari・Firefox (PC とスマホ)
- 性能: 初回の読み込みが 1 MB 未満 (Vercel の無料枠と、スマホの回線を考えて)

## 見直しの条件

- 問題を自動生成に切り替えるとき、公開後に問題を足すとき、遊び手が 1 日 1 万人を超えたとき
