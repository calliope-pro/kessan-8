## 1. 結論

- **全部品を、設計 (静的サイト・外部通信なし・フレームワークなし・初回 1 MB 未満) の範囲で作れる**。1 MB の予算に対して、部品の追加で効くのは問題データ (60 問で約 160 KiB、導いた。設計 §4.3) で、部品のコード・CSS・SVG は小さい (仮定: 圧縮後 100 KiB 以下。いまの dist は gzip で 927 B、測った)。
- **問題データの追加項目は少なく、どれも問題ごとの作業を増やさない**。セル ID・異変の画面 ID とセル ID・印の照合は、**設計に既にある `path` で足りる** (§4)。短信 ↔ IR の対応表 (T3) と検算の式 (R2) は、問題に持たせず、**検証器の規則から作る** (二重に持つと食い違うため)。足りない項目は 3 つの任意項目 (`Company.business`・`AnomalyKind.tip`・`Problem.tier`) と見本のファイルだけで、どれも会社・異変の種類・難しさの段の側にある (§4.2)。
- **技術から見て低リスクで効果の大きい組み合わせ**: 操作の筋の T1 + T2 + T4 (印・検算・道具の段階) と R1〜R3 (場所の示し・検算の見せ方・印の照合)、舞台の筋のうち CSS だけで作れる V1・V2・V4 と R4〜R6、進行の筋の P0・P3 と、手順を直した P1。**慎重に扱うもの**: P4 (持ち時間。理由は §3.3)、V3 (社章。作るのは小さいが、実在の商標との照合に人の目が要る)、T3 (並べて見る。作りは中〜大で、スマホでは短い対応表だけが成り立つ)。
- **スマホ (320〜414 px) で、タップの的 44×44 CSS px 以上の表・タブ・印の切替・検算の置き場は、横にはみ出さずに置ける** (測った。§2)。ただし 44 px の行にすると 1 画面が縦に長くなる (貸借対照表で 1,301 px、キャッシュ・フローで 1,389 px。測った)。

## 4. 問題データへの追加項目 (single source of truth)

### 4.1 追加が要らない・問題に持たせないもの

| 相談の項目 | 見立て | 理由 |
| --- | --- | --- |
| 数字・文のセルごとの ID | **追加しない** | 設計 §4.1 の `path` (`<doc>.<path>`) が既にセル ID。文字列のセル (`notes.goingConcern`・`commentary` など) も同じ形。印・検算・異変の場所・`data-path` がすべて同じ ID で結ばれる |
| 異変の画面 ID・セル ID | **追加しない** | `anomaly.places[].path` の先頭が画面 ID (`header` は資料の 1 画面目)。`screenOf(place)` で引く |
| 短信 ↔ IR の対応表 (T3) | **問題には持たない。共通の表 1 つ (`src/domain/links.ts`)** | 対応は全問で同じ (売上高 ↔ ハイライトの売上高 など)。**検証器の資料間の規則と同じ表から作る**ので、対応が実際に一致することを規則が確かめる。試作 `check_ir.py` の「短信-」の規則が **20 件** (測った: 数えた) で、対応表の大きさはこれが目安 |
| R2 検算の式 | **持たない** | 数値は資料にあり、式の文字列は検証器の規則が作る (§3.4)。持つと数字の出所が 2 つになる |
| 印と異変の照合 (R3) | 追加しない | 印の集合 (セル ID) と `places` の突き合わせ |

### 4.2 足す項目 (どれも会社・異変の種類・難しさの側で、問題ごとの作業を増やさない)

| 項目 | 場所 | 要る部品 | 内容 |
| --- | --- | --- | --- |
| (配色) | 業種 → 配色の表 (ui の定数。問題データには持たない) | V3 | `Company.industry` から引く。会社ごとに配色を書くと、業種ごとの配色の知識が会社の数だけ写される |
| (社章・配色) | 会社の設定 companies.md §4 にあり、`Company.emblem`・`Company.colors` として型に入っている | V3 | 追加の項目ではない |
| `business: string` | `Company` | P2 | 事業の説明 1 文。数字・増減の語を含めない |
| `tip: string` | `AnomalyKind` (anomaly-kinds.json) | R7 | 種類ごとの 1 行 |
| `tier: 1 \| 2 \| 3` | `Problem` | P1 | 難しさの段。正常な問題にも付ける |
| 見本のファイル | `src/data/samples/<difficulty>.json` | P0 | `{ problem: Problem (anomaly: null), notes: 画面 ID → 注釈の文 }`。`problems/` の外なのでプールに混ざらない |

**過剰なもの**: 問題ごとの導入文 (事業は会社の性質で、`Company.business` で足りる)・セル ID の別項目・式の文字列。**足りないもの**: 上の表の項目以外は、相談の部品には無い。

これらは**設計の型に任意の項目として足す** (後述 §7。選ばれた部品の分だけ検証器で必須にする)。会社の設定 (#24・#39) と異変の種類の一覧 (#40) を作るときに `business`・`tip` を埋めるのは 1 件あたり 1 文なので、部品が選ばれる前に埋めておくほうが、後で全件に足すより安い (見立て)。

## 5. 確かめ方 (E2E と単体)

受け入れ条件 1〜4・9 の E2E (設計 §7) は、出題を `?seed=N` で固定し、表示中の問題の `data-problem-id` から問題の JSON を読んで正解を知る形。部品はその上で次のとおり。

| 項目 | 確かめ方 | 根拠 |
| --- | --- | --- |
| 出題の抽選を seed で固定できるか | **できる**。`draw` は乱数 `rng` と履歴を**引数にとる純粋な関数**で、種つき乱数 (mulberry32) を渡す。P1 の重み・P3 の履歴も同じ入れ物で決定的 | 設計 §5.3。P3 の履歴は引数なので、テストは空の履歴から始める |
| P1 の段の分布 | 単体: 種を固定した多数の出題 (例: 1,000) で、序盤・中盤・終盤の枠が狙いの段になる割合が、**許容の下限以上**であることを確かめる。許容は実際のプールで決める。**目安は測った値**: 手順 B で、12 社・段 11:9:5 の pool なら 1〜3 社目 1.00、4〜6 社目 0.98 以上、7〜8 社目 0.90・0.77 (§6-6)。8 社だと 1〜3 社目 1.00、8 社目 0.64。許容を決めないと、効き目の弱い手順を捕まえない | 測った |
| T1・T2 | E2E: スイッチを入れてセルを押す → `data-marked`。2 つ選ぶと結果が、テストが問題の JSON から計算した値と一致。スイッチを切ると反応しない | 見立て |
| T3 | E2E: むずかしいで並べて見る → 対応表の全組が出る。単体: 全組で正常な問題の値が一致 | 見立て |
| `prefers-reduced-motion` | CSS は `@media (prefers-reduced-motion: reduce)` で `animation`・`transition` を止める。JS で動かす遷移 (R5) は `matchMedia` を見て省く。**E2E で `page.emulateMedia({ reducedMotion: 'reduce' })` を当てると、`matchMedia` が真になり、CSS の `animation-name` が `none` になる (測った: Chromium、Playwright 1.64.1)** | 測った |
| 時間に依る部品 (P4。選ぶ場合) | Playwright の `page.clock` で偽の時計を入れ、`runFor` で進める。**`fastForward` は繰り返しのタイマーを 1 回しか進めない** (測った: 30 秒進めて `setInterval` 1 秒が 1 回。`runFor(30000)` は 30 回) ので、`runFor` を使う | 測った |
| P5 の保存の失敗 | 初期スクリプトで `Storage.prototype.setItem` を例外にして遊べることを確かめる。`localStorage` が禁じられた環境の本物の例外は `SecurityError` (測った: `about:blank` で `localStorage` を使うと出る。ブラウザのプライベートウィンドウは測っていない) | 測った |
| V2 のコントラスト | 単体: 8 段の背景色と文字色から、コントラスト比 (WCAG の式) を計算し、基準 (本文 4.5:1) 以上を確かめる。色は CSS 変数ではなく TypeScript の定数にして、CSS はそこから生成するか、同じ値を指す (二重に書かない) | 見立て |

## 6. 技術から見た、案に足りない・危ない点

1. **CSP が `style` 属性を許さない** (vercel.json の `style-src 'self'`。足場 #37 の E2E が違反を捕まえる)。V2 の背景・V3 の配色・T 系の強調を、`element.setAttribute('style', …)` や style 属性つきの HTML 文字列で作ると、公開版で崩れる。**CSSOM (`el.style.width = …`) は使える** (測った: 試作の変異で、`el.style.width = '600px'` が CSP の下で効き、E3 を赤にした)。勧め: **`data-` 属性 + CSS のセレクタ**で状態 (段・印・強調) を表す。SVG の社章も、`style` 属性でなく表現属性 (`fill` など) と CSS のクラスで塗る。
2. **印の付け外しは「状態」**: 設計 §5.1 の `reading` に `marks` を足す (T1 を選ぶ場合)。`revealed` には持ち越し、R3 が使う。`RESTART`・`NEXT` では空にする。
3. **PC のキーボードと読み上げ**: セルを押せるものにする (T1) と、`button` 相当の役割と `aria-pressed` が要る。要件に無い (PC 優先・スマホ可) が、押せる要素にフォーカスが無いと PC の操作が成り立たない。工数は T1 に含めた。
4. **T3 の対応表の定義**: 資料間の食い違いを「同じ定義の数字どうし」に限る (tech-assessment §5-4)。対応表の項目が、実在の様式でも一致するもの (売上高・営業利益・純利益・セグメント) に限られることを、表を作る人 (問題の制作の担当) が確かめる。
5. **R2 の式と `anomaly.explanation` の数字が食い違う恐れ**: 異変の問題の根拠の式は規則が作り、答え合わせの文は問題データの `explanation` が持つ。2 つの数字が食い違うと、画面の中で自己矛盾する (失敗 2)。単体テストで、規則が作った式の数字が `explanation` に含まれることを確かめる (任意の整合確認)。
6. **P1 は、設計 §5.3 の初版の出題手順 (会社を先に選ぶ) では効かなかった。手順を直した** (レビューの指摘を、自分でも測って確かめた)。`docs/plans/spike/draw-tiers.py` で、25 問を段 11:9:5 に割り、どの会社も異変あり・なしの両方を持つ pool を 400 通り作り、各 50 回出題した (測った)。狙いの段 (1〜2 社目 = 1、3〜5 社目 = 2、6〜8 社目 = 3) が当たる割合は、**初版の手順 A (会社を先に 8 社選ぶ → あり/なし → その会社の問題から狙いに近いもの)**: 会社 8 社の pool で 1〜2 社目 0.56・0.57、3〜5 社目 0.48〜0.49、6〜8 社目 0.28〜0.29。1 社目に段 3 (紛らわしい) が出る割合 12.3%。12 社では 0.45・0.44、0.37、0.21 と**むしろ下がる** (選ぶ会社が増えると、その会社が狙いの段を持たない)。**枠を先に決める手順 B (各枠の あり/なし を先に引く → 1 社目の枠から順に、重複しない会社を増加路で割り当て、当てられない枠だけその枠の段を近い段へ緩める。先の枠は緩めない)**: 8 社で 1〜3 社目 1.00、4 社目 0.99、5〜6 社目 0.96・0.97、7 社目 0.84、8 社目 0.64、1 社目に段 3 が出る割合 0%。12 社で 1.00・1.00・1.00・0.99・0.98・0.98・0.90・0.77、段 3 は 0%。終盤の枠の当たりが下がるのは、先の枠を優先したため (紛らわしい問題が 5 問と少ない)。**手順 B に直し (設計 §5.3)、P1 の工数を 3 → 4 h にした**。段の指定を使わなければ (P1 を採らなければ)、手順 B は段を無視して あり/なし だけで会社を割り当てるだけで、同じ関数で足りる。(途中の試行: 緩める枠を後ろから選ぶ全体の緩め方は、8 社で 1〜2 社目 0.95・0.94 と、先の枠を優先する手順 B より悪かった。測った)
7. **実機のスマホ**: この見立てのスマホの測定は macOS の Chrome のみ。iOS Safari の長押し・拡大・戻るのスワイプ、Firefox は、公開の通し (#30) で人の目に頼る (測っていない)。
8. **期限**: 全部入りの合計は 37.5 h (仮定、実装 h の係数 1.5 の前)。係数をかけると 56.25 h。U2 は 21.5 h・U1 は 14 h・U3 は 15 h (V3 は、社章が会社の設定の記号 1 字と分かって 3 → 1.5 h に直した)。共通の土台 (#27・#28) は別。部品を選ぶときは、**問題の数・正しさに先行させない** (案の制約のとおり)。

## 8. 範囲と限界

- **測った**のは、スマホ幅での表・タブ・的の大きさの収まり (macOS の Chrome)、`prefers-reduced-motion` の効き・偽の時計・保存の失敗の挙動 (Chromium)、CSP の下での CSSOM の効き、難しさの段を入れた出題の 2 つの手順の当たり率 (§6-6)、事業側の数字の再計算 (experience.md M3・M4・U3 の期待の問題数 24.8、146.3、25 問を超える割合 35.3%・87.2%、段ごとの出会う回数 10.7・9.3・4.8 はすべて一致した)。
