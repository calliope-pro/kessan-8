## 1. 結論

- **全部品を、設計 (静的サイト・外部通信なし・フレームワークなし・初回 1 MB 未満) の範囲で作れる**。1 MB の予算に対して、部品の追加で効くのは問題データ (60 問で約 160 KiB、導いた。設計 §4.3) で、部品のコード・CSS・SVG は小さい (仮定: 圧縮後 100 KiB 以下。いまの dist は gzip で 927 B、測った)。
- **問題データの追加項目は少なく、どれも問題ごとの作業を増やさない**。セル ID・異変の画面 ID とセル ID・印の照合は、**設計に既にある `path` で足りる** (§4)。短信 ↔ IR の対応表 (T3) と検算の式 (R2) は、問題に持たせず、**検証器の規則から作る** (二重に持つと食い違うため)。足りない項目は 5 つだけで、どれも会社・異変の種類・難しさの段の側にある (§4.2)。
- **技術から見て低リスクで効果の大きい組み合わせ**: 操作の筋の T1 + T2 + T4 (印・検算・道具の段階) と R1〜R3 (場所の示し・検算の見せ方・印の照合)、舞台の筋のうち CSS だけで作れる V1・V2・V4 と R4〜R6、進行の筋の P0・P1・P3。**慎重に扱うもの**: P4 (持ち時間。理由は §3.3)、V3 (社章。作るのは小さいが、実在の商標との照合に人の目が要る)、T3 (並べて見る。作りは中〜大で、スマホでは短い対応表だけが成り立つ)。
- **スマホ (320〜414 px) で、タップの的 44×44 CSS px 以上の表・タブ・印の切替・検算の置き場は、横にはみ出さずに置ける** (測った。§2)。ただし 44 px の行にすると 1 画面が縦に長くなる (貸借対照表で 1,301 px、キャッシュ・フローで 1,389 px。測った)。

| 短信 ↔ IR の対応表 (T3) | **問題には持たない。共通の表 1 つ (`src/domain/links.ts`)** | 対応は全問で同じ (売上高 ↔ ハイライトの売上高 など)。**検証器の資料間の規則と同じ表から作る**ので、対応が実際に一致することを規則が確かめる。試作 `check_ir.py` の「短信-」の規則が **20 件** (測った: 数えた) で、対応表の大きさはこれが目安 |
| R2 検算の式 | **持たない** | 数値は資料にあり、式の文字列は検証器の規則が作る (§3.4)。持つと数字の出所が 2 つになる |
| 印と異変の照合 (R3) | 追加しない | 印の集合 (セル ID) と `places` の突き合わせ |

### 4.2 足す項目 (どれも会社・異変の種類・難しさの側で、問題ごとの作業を増やさない)

| 項目 | 場所 | 要る部品 | 内容 |
| --- | --- | --- | --- |
| `palette: string` | `Company` (companies.json) | V3 | 業種の配色 ID (4〜6 種、案の仮定) |
| `emblem: { shape: string; ... }` | `Company` | V3 | 社章の幾何形の指定。生成は純粋な関数 |
| `business: string` | `Company` | P2 | 事業の説明 1 文。数字・増減の語を含めない |
| `tip: string` | `AnomalyKind` (anomaly-kinds.json) | R7 | 種類ごとの 1 行 |
| `tier: 1 \| 2 \| 3` | `Problem` | P1 | 難しさの段。正常な問題にも付ける |
| 見本のファイル | `src/data/samples/<difficulty>.json` | P0 | `{ problem: Problem (anomaly: null), notes: 画面 ID → 注釈の文 }`。`problems/` の外なのでプールに混ざらない |

**過剰なもの**: 問題ごとの導入文 (事業は会社の性質で、`Company.business` で足りる)・セル ID の別項目・式の文字列。**足りないもの**: 上の表の 6 つ以外は、相談の部品には無い。

## 5. 確かめ方 (E2E と単体)

受け入れ条件 1〜4・9 の E2E (設計 §7) は、出題を `?seed=N` で固定し、表示中の問題の `data-problem-id` から問題の JSON を読んで正解を知る形。部品はその上で次のとおり。

| 項目 | 確かめ方 | 根拠 |
| --- | --- | --- |
| 出題の抽選を seed で固定できるか | **できる**。`draw` は乱数 `rng` と履歴を**引数にとる純粋な関数**で、種つき乱数 (mulberry32) を渡す。P1 の重み・P3 の履歴も同じ入れ物で決定的 | 設計 §5.3。P3 の履歴は引数なので、テストは空の履歴から始める |
| P1 の段の分布 | 単体: 多数の種 (例: 1,000) で出題し、序盤・中盤・終盤の枠の段の割合が重みの許容に入ることを確かめる (確率的な性質は、固定した多数の種で決定的に確かめる) | 見立て |
| T1・T2 | E2E: スイッチを入れてセルを押す → `data-marked`。2 つ選ぶと結果が、テストが問題の JSON から計算した値と一致。スイッチを切ると反応しない | 見立て |
| T3 | E2E: むずかしいで並べて見る → 対応表の全組が出る。単体: 全組で正常な問題の値が一致 | 見立て |
| `prefers-reduced-motion` | CSS は `@media (prefers-reduced-motion: reduce)` で `animation`・`transition` を止める。JS で動かす遷移 (R5) は `matchMedia` を見て省く。**E2E で `page.emulateMedia({ reducedMotion: 'reduce' })` を当てると、`matchMedia` が真になり、CSS の `animation-name` が `none` になる (測った: Chromium、Playwright 1.64.1)** | 測った |
| 時間に依る部品 (P4。選ぶ場合) | Playwright の `page.clock` で偽の時計を入れ、`runFor` で進める。**`fastForward` は繰り返しのタイマーを 1 回しか進めない** (測った: 30 秒進めて `setInterval` 1 秒が 1 回。`runFor(30000)` は 30 回) ので、`runFor` を使う | 測った |
| P5 の保存の失敗 | 初期スクリプトで `Storage.prototype.setItem` を例外にして遊べることを確かめる。プライベートモードの本物の例外は `SecurityError` (測った: `about:blank` で `localStorage` を使うと同じ例外) | 測った |
| V2 のコントラスト | 単体: 8 段の背景色と文字色から、コントラスト比 (WCAG の式) を計算し、基準 (本文 4.5:1) 以上を確かめる。色は CSS 変数ではなく TypeScript の定数にして、CSS はそこから生成するか、同じ値を指す (二重に書かない) | 見立て |

## 6. 技術から見た、案に足りない・危ない点

1. **CSP が `style` 属性を許さない** (vercel.json の `style-src 'self'`。足場 #37 の E2E が違反を捕まえる)。V2 の背景・V3 の配色・T 系の強調を、`element.setAttribute('style', …)` や style 属性つきの HTML 文字列で作ると、公開版で崩れる。**CSSOM (`el.style.width = …`) は使える** (測った: 試作の変異で、`el.style.width = '600px'` が CSP の下で効き、E3 を赤にした)。勧め: **`data-` 属性 + CSS のセレクタ**で状態 (段・印・強調) を表す。SVG の社章も、`style` 属性でなく表現属性 (`fill` など) と CSS のクラスで塗る。
2. **印の付け外しは「状態」**: 設計 §5.1 の `reading` に `marks` を足す (T1 を選ぶ場合)。`revealed` には持ち越し、R3 が使う。`RESTART`・`NEXT` では空にする。
3. **PC のキーボードと読み上げ**: セルを押せるものにする (T1) と、`button` 相当の役割と `aria-pressed` が要る。要件に無い (PC 優先・スマホ可) が、押せる要素にフォーカスが無いと PC の操作が成り立たない。工数は T1 に含めた。
4. **T3 の対応表の定義**: 資料間の食い違いを「同じ定義の数字どうし」に限る (tech-assessment §5-4)。対応表の項目が、実在の様式でも一致するもの (売上高・営業利益・純利益・セグメント) に限られることを、表を作る人 (問題の制作の担当) が確かめる。
5. **R2 の式と `anomaly.explanation` の数字が食い違う恐れ**: 異変の問題の根拠の式は規則が作り、答え合わせの文は問題データの `explanation` が持つ。2 つの数字が食い違うと、画面の中で自己矛盾する (失敗 2)。単体テストで、規則が作った式の数字が `explanation` に含まれることを確かめる (任意の整合確認)。
6. **P1 と設計 §5.3 の出題手順の接続**: 「会社を先に選ぶ」は、枠ごとに段が違うと、選んだ会社がその段の問題を持たないことがある。段の数が足りないときは近い段へ寄せる (失敗させない)。データの条件を、難易度ごと・段ごとに検証器で確かめる (§3.3)。
7. **実機のスマホ**: この見立てのスマホの測定は macOS の Chrome のみ。iOS Safari の長押し・拡大・戻るのスワイプ、Firefox は、公開の通し (#30) で人の目に頼る (測っていない)。
8. **期限**: 全部入りの合計は 38 h (仮定、実装 h の係数 1.5 の前)。係数をかけると 57 h。U2 は 21.5 h・U1 は 15.5 h・U3 は 14 h。共通の土台 (#27・#28) は別。部品を選ぶときは、**問題の数・正しさに先行させない** (案の制約のとおり)。

## 7. 基本設計の直し (この見立てを受けて)

設計 (#36 合意済み) の型に、**任意の項目**として §4.2 の 5 つを足す (部品が選ばれたら検証器で必須にする)。`Company.palette`・`Company.emblem`・`Company.business`・`AnomalyKind.tip`・`Problem.tier`。見本は型の変更が要らない (`Problem` をそのまま使う)。設計 §5.1 の `reading` に、T1 を選んだ場合の `marks` を足す提案は、選ばれてから設計を直す (§6-2)。
